## 2. V2 要交付的行为

用户打开同一个 HTTPS 地址，注册、验证邮箱、登录，得到空白的个人工作区；上传自己的简历、确认事实、导入岗位、提交生成任务、审核并下载自己的 PDF。退出后，原页面不能继续读取私人内容；重新登录后可以找回自己的材料和任务。

容量设计假设：**100 个注册账号，10 人同时浏览/编辑，10 人在短时间内提交生成。** 不是 100 个模型任务同时执行，也不是性能承诺。初始配置建议全站同时运行 2 个重任务，其中 PDF 渲染最多 1 个；每人最多 1 个执行中任务及 1 个排队任务。负载测试后调整，注册数不直接决定机器配置。

上线范围包括中英文现有主流程、用户隔离、可恢复任务、有限额度和基本运维。不加入付费订阅、团队共享、自动投递、扫描件 OCR、全网爬取、多 Agent、移动应用或微服务。Jev 实验继续默认关闭。

## 3. 重要选择与代价

### 3.1 账号：推荐复用 AWS，使用 Cognito

现有 [public_access.py](https://github.com/YIEXUWOSHIDUDE/Feiran/blob/9d670cde2a4af95d2470b58e08e35c2a1514aa34/public_access.py) 是一份固定所有者凭据的 HTTP Basic 验证，不能扩成多人共用密码。

推荐 Cognito 托管注册、邮箱验证、登录与密码找回；应用仍负责账户状态、用户归属、会话和权限。另一方案是应用自行保存密码和处理邮件恢复，少一个外部账号服务，但增加凭据安全和邮件运行负担，当前不选。Cognito 的套餐、邮件发送配置、域名和费用需在创建资源前核定，本方案不声称免费。

拟采用授权码流程加 PKCE；后端核验登录结果并映射 `(issuer, subject)` 到稳定的内部 `user_id`，不能用可修改邮箱作为资料主键。浏览器使用 HttpOnly、Secure、SameSite 会话 Cookie，写请求带会话级 CSRF 防护；校验回调地址、state、nonce、令牌签名/颁发者/受众/期限。使用维护中的协议库，不自制密码或令牌算法；具体依赖和版本在实施前核对。

会话存在服务端，可退出、到期和停用；退出先撤销本地会话，再结束身份提供方会话。账户停用后，排队任务不再启动，执行中结果不得发布。关闭自助注册用于分批试点，验收和费用配置通过后再开放，应用账户上限先设 100。现有所有者凭据不能作为访问全部用户资料的后门；本地单用户模式只能显式启用，并拒绝在公网模式下作为登录失败的回退。

依据：[Cognito 托管登录](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-userpools-managed-login.html)、[授权码与 PKCE](https://docs.aws.amazon.com/cognito/latest/developerguide/authorization-endpoint.html)。

### 3.2 数据：推荐共享 SQLite，所有私人记录有明确归属

选项一是每人独立数据库，较易沿用原代码，但需要逐份迁移和备份；选项二是共享 SQLite、在数据访问接口中强制用户范围；选项三是直接迁移 PostgreSQL，增加独立数据库服务、连接管理、部署和备份成本。

**推荐选项二。** 当前目标允许单机，100 个账号尚不是引入数据库服务的理由。SQLite 同一数据库一次只能有一个写者，因此模型调用、网页抓取和 PDF 渲染必须在短数据库事务之外；不能保留全站长时间写锁。若验收表明短事务仍持续拥塞，或明确需要多台应用主机，再迁移 PostgreSQL。[SQLite 官方适用范围](https://sqlite.org/whentouse.html)

这不是简单给现有表增加一个字段：现有权威状态分散在两个 SQLite 文件、profile JSON、岗位步骤文件和中断提示中。V2 用共享业务数据库管理用户、事实版本、profile 版本、材料版本、批准、任务及文件索引；现有 JSON 业务内容尽量原样保留为版本载荷，不重写规则算法。文件只保存不可变的上传/产物，数据库决定哪个版本有效，避免两套权威状态。

所有私人主键/外键关联都带用户范围，或由等效约束保证同一用户；不能只在前端过滤。材料读取接口要求认证用户和材料 ID，内部完成归属校验。不要保留可供普通网页调用的无用户范围读取入口。迁移工具是独立离线路径，不是绕过权限的在线接口。

公共岗位正文可以作为公共缓存复用，但关注公司、收藏、生成状态、匹配结果和排序缓存属于个人。现有 `listings.py` 的 `matched_key`、`matched_tags` 不能作为所有人共享的私人匹配结果。公共缓存只接受已验证的公开来源，不混入用户粘贴内容和简历文字。

### 3.3 文件：先保留私有数据卷，暂不迁移全部产物到 S3

现有加密 EBS 与私有 S3 备份可以继续使用。先以服务端生成的用户/产物编号组织私有文件，预览和下载都经过后端认证、归属与版本检查；浏览器不能提交文件系统路径。跨用户去重不得泄露文件是否存在。

文件先在受控临时目录完整写出，再登记为可用产物；数据库登记失败不能显示导出成功，孤立临时产物按明确规则清理。备份期间暂停任务领取与写入，等待执行中任务退出或记录可恢复状态，再保存数据库和文件的一致副本。停机窗口是此方案的代价，需实测并告知试用者。

用户可删除自己的材料并申请删除账户；立即阻止访问与新任务，清理在线数据和临时上传，备份按已公布期限到期删除。保留必要的删除标记，使恢复旧备份后不会把已删除账户重新开放。上线前验证删除和恢复的组合，不承诺备份即时擦除。

### 3.4 任务：数据库记录进度，一个应用进程内有限执行

现有 `web.py:create_app` 为整个实例创建一个 Workspace、一组资料路径和 `asyncio.Lock`；`one_change_at_a_time` 等待上限 90 秒。`prepare_cv`、缺口检查和 PDF 导出在请求内执行。DeepSeek 单次 HTTP 超时为 120 秒，且有有限重试；公网模板的 origin 读取超时为 120 秒。**由此推断长任务可能超过请求等待窗口；这不是本轮复现的线上故障。**

V2 提交任务后快速返回任务 ID；页面查询持久化状态。状态为 `queued → running → succeeded / failed / interrupted / superseded`，取消另记 `cancelled`；有可用原文草稿但改写失败时仍显示阶段降级，不假装全部成功。刷新页面不重新生成。

任务保存所属用户、操作类型、精确输入版本、请求幂等键、阶段、尝试次数、截止时间和结果版本。唯一约束绑定 `(user_id, operation, idempotency_key)`；同键不同输入返回冲突，同键重试返回原任务，用户主动重新生成用新键。

第一版只有一个应用进程和有上限的后台执行器，不开启多个 Uvicorn worker，也不新增 Redis/Celery。数据库短事务领取任务并记录执行令牌；启动恢复先处理遗留的 running 任务。超时或取消后的迟到结果不能覆盖新结果，发布时同时校验执行令牌与输入版本。明确进程未退出前不把同一任务交给另一个执行者。

保证同一请求只发布一个业务结果；**不承诺外部模型调用恰好一次**，因为请求已收费但响应丢失时无法凭本地状态确认。此类失败记录费用未知，不无限自动重试。重试上限、任务总时限与各阶段时限一起控制。

所有付费或重操作都进入同一额度控制，包括简历解析、岗位抽取、改写、布局、缺口/建议和 PDF；不能只限制“生成”按钮。开始前原子预留额度，结束后结算可确认用量；有每日用户额度和全站额度、关闭新任务的开关、队列上限。额度不只靠浏览器；满队列返回明确的 429 和重试提示。具体每日额度及费用上限在试点前由预算确定，并必须有有限配置值才能开放注册。

数据告知必须区分处理阶段：历史设计允许上传结构解析向 DeepSeek 发送学校/雇主标题，按岗位处理才额外遮盖已知学校和雇主；从未出现在 profile 中的私人实体仍可能漏识别。不能统一写成“完全匿名”。V2 每位用户首次使用相应模型功能前明确看到数据去向；未同意时不调用。所有者过去对自己资料的许可不能替代新用户的选择。

## 4. 最小数据与代码职责

下列是待实现职责，不是要求立即建立所有空文件或通用框架。

| Module | Interface / 调用者 | 权威状态与职责 |
|---|---|---|
| 身份与会话 | 登录回调、退出、请求认证；网页入口调用 | 认证身份、内部用户、会话、停用；不读取简历 |
| 用户工作区 | 带 `user_id` 的事实/岗位/材料读写；网页和任务调用 | 归属、版本、同用户关联、冲突；不调用模型 |
| 生成流程 | 精确输入快照 → 草稿和阶段结果；任务执行器调用 | 复用 `cv.py`、`claims.py`、`gaps.py` 等规则；输出不能确认事实或批准 |
| 任务执行 | 提交、查看、重试/取消；网页调用 | 去重、额度、状态、有限执行、迟到结果拒绝 |
| 文件与备份 | 已授权产物读取/登记、离线备份恢复 | 私有字节、原子发布、备份一致性；不替用户作批准决定 |

关键记录至少包括：用户；版本化事实及确认；按语言的 profile 版本；JD 快照；材料版本及所用输入；用户批准；任务；文件索引。批准绑定审核人、材料、JD、相关事实/profile 版本；生成结果不能写入批准状态。

学习重点：**身份认证回答“是谁”，用户工作区接口回答“可以碰哪份资料”**。第二个重点是把“模型已经返回”与“结果已安全保存、可供用户使用”分开；数据库只在后一条件成立时标记任务完成。

## 6. 小步实施顺序与验收

每一步单独形成可审阅增量；先确认方案再实现，不一次生成整个系统。下列是计划切分，不是已创建的 PR。

1. **归属与存储闭环（第一个增量）**：在隔离工作区用两个合成用户，完成事实导入/确认、按语言保存 profile、建立 JD 与材料记录的归属。前端尚不开放注册；测试身份入口只存在于测试，不能部署为公网绕过。验收：A/B 可使用相同事实 ID 和岗位来源而互不影响；交叉读取/修改/引用全部失败。保留旧单人启动路径及现有离线回归，迁移只对合成副本演练。
2. **真实登录与所有私人路由隔离**：接 Cognito 会话，将事实、上传提案、岗位、关注列表、通知、预览、下载全部接到有用户范围的接口。新用户没有预置他人资料；退出/过期/停用立即拒绝。会话 Cookie、回调、CSRF、CloudFront 转发/不缓存及直接源站防绕过一起检查。
3. **异步生成、额度与版本发布**：网页提交/轮询；重操作统一调度；模型只接收当前用户的输入快照。用户在生成期间修改事实，旧结果不能覆盖新材料，也不能沿用批准；导出期间版本改变不得发布成当前最终版。
4. **完整迁移与恢复**：用合成的 V1 工作区先演练。明确指定旧所有者账户，不能把旧资料赋给“第一个注册者”。保持原文/版本载荷，验证后再启用；无法证明原批准有效的材料回到待审核，绝不补造批准。保留旧目录和备份，升级数据格式号。回退必须同时处理代码与数据；V2 已产生的新资料须先保全，不能恢复旧备份后无声丢弃。
5. **100 人试点验收**：完成下表、B4 演练与 B6 有限评估；先邀请少量独立用户，再放开到 100 个账号。每一阶段记录错误与费用后再扩大。对外发布仍按已有人工发布流程，不因合并自动上线。

| 验收输入 | 必须观察到的结果 |
|---|---|

**① 正式登录与全部私人路由隔离（B1）**

- 新增 [identity.py](../identity.py)：Cognito 授权码 + PKCE（S256）、`state`、`nonce` 与浏览器绑定 Cookie；一次登录尝试只能被发起它的浏览器消费一次，10 分钟过期。令牌端点用 `client_secret_basic`；ID token 由 PyJWT 按 JWKS 校验 RS256 签名、`iss`、`aud`、`exp`、`iat`、`token_use=id` 和 `nonce`；`return_to` 只接受站内路径。新增依赖 `PyJWT==2.15.1`、`cryptography==50.0.2`。
- 新增独立应用 [web_v2.py](../web_v2.py)（`web.py` 的单用户行为与部署路径不变）：服务端会话只存令牌哈希，绝对 12 小时、空闲 2 小时；`__Host-` Cookie（HttpOnly、Secure、SameSite=Lax）；会话级 CSRF（页面 meta → `X-Workbench-Token`，另核对 Origin）；Host 白名单；`no-store` 等安全头；请求体上限（JSON 256 KB、PDF 5 MB）。退出先撤销本地会话，再跳转 Cognito 退出；过期、停用、删除后下一次请求即 401。

**③ 异步任务与额度**

- 上传解析、岗位导入（粘贴/URL/岗位列表）、准备/改写/版面、缺口检查、PDF 导出都只能经任务提交，立即返回 202 与任务 ID；持久化输入、幂等键 `(user_id, operation, key)`（同键同输入返回原任务，同键不同输入 409）、阶段、尝试次数、执行令牌与截止时间。
- [task_runner.py](../task_runner.py)：进程内有界执行器，全站同时 2 个、其中 PDF 1 个；每人 1 个执行中 + 1 个排队；全站排队上限。模型调用、网页读取和 PDF 渲染都在数据库写事务之外。发布时同时核对执行令牌与基线版本，取消、超时、被打断或输入已被取代的迟到结果一律拒绝。重启把遗留的 running 标为 interrupted，不自动重跑；同一请求最多尝试 3 次；排队超过 15 分钟失效，单任务 10 分钟超时。

### 9.2 设计决定与偏离原方案之处（建议验收时重点审查）

1. **独立的 `web_v2.py`**，不改造 `web.py`：当前线上单用户版本不受影响，V2 也不存在退回所有者口令的路径。代价是 V1 退役前两套路由并存。
2. **上传提案与 PDF 存进 SQLite**，偏离 §3.3“文件只保存不可变的上传/产物”：发布与数据库记录在同一事务内完成，在线备份是一致快照，删除账户时 `secure_delete` 覆盖内容，也避免文件与数据库两套权威状态。代价是数据库随 PDF 增长（合成 PDF 每份 46–94 KB）；库体积或备份时长成为问题时再改成文件 + 索引。
3. **备份不暂停任务**，偏离 §3.3“备份期间暂停任务领取”：全部状态在一个 SQLite 文件里，在线备份已是一致时刻；当时在运行的任务恢复后成为 interrupted，不会自行重跑或发布。
4. 公司岗位列表刷新在请求内执行（有并发、频率与缓存限制），没有做成任务；从列表建岗位是任务。
5. 单进程、单 Uvicorn worker、SQLite WAL；试点前不引入 PostgreSQL/Redis（与 §3.2、§3.4 一致）。
6. V1 各岗位的历史目录不迁移，留在 V1 目录并在迁移报告中列出。

### 13.1 R3：粘贴岗位在响应丢失后重发

根因有两层。`prepare_pasted_jd` 每次都写入新的 `captured_at`，而 `_new_job` 拿含时间戳的整份 JD 比较；此外，建岗位和排任务不在同一事务里，同键配不同正文时，岗位会先建好，然后才在排任务时冲突。

修复：
- `_new_job` 比较时去掉服务器写入的 `captured_at`。同一请求找到首次采集的岗位，采集时间不变；同一 request_id 配不同正文仍然冲突（第一阶段的冲突测试照样通过）。
- `task_job`（从 URL 或岗位列表建岗位的任务）在重试时沿用第一次尝试建的岗位和采集时间。以前，重试重新读取岗位会被判为“不同 JD”，任务因此失败。
- 新增 `UserWorkspace.paste_job`，粘贴路由改用它，岗位和“查找要求”任务在同一事务里处理：
  - 相同正文重发（同键、新键或不带键）都得到原岗位。要求已找到时返回 200 `existing`；该岗位已有排队、运行中或已完成的查找任务时返回那个任务，不排第二个。
  - 同一个键配另一段正文返回 409，整个请求回滚，什么都不保存。
  - 因额度、队列或数据同意暂时排不上任务时，岗位保留并返回原因（与原行为一致）；之后同一请求再发，就排上任务。
- `_find_and_prepare` 在调用模型之前先比较要求版本：已过期的查找直接记为 superseded，不调用模型，本次额度退回。
- 保存后自动重新准备简历（添加或决定要求、接受或写入缺口行）不再沿用页面的请求键，改由服务器状态命名。页面的键代表用户那一次保存；同一个键被重复使用时，新的保存不会拿到旧的准备任务。以前会拿到，简历就不会按新决定重新准备。

新增测试：
- web：
  - 粘贴重发（同键、新键、无键）都得到原岗位，采集时间不变，没有第二个任务或模型调用。
  - 同键配另一段正文 409，不新增岗位或任务。
  - 第一段还在处理时用新键再贴，返回同一个任务。
  - 暂停任务时粘贴，岗位保留；恢复后同一请求排上任务并完成。
  - 已过期的查找不调用模型，额度退回。
  - 同一个键用于两次不同的要求决定，各自得到新的准备任务，简历按最新决定准备。
- store：
  - 同一 request_id 只换采集时间，得到原岗位和原时间；换正文仍是 409。
  - 任务重试时读到更新过的岗位，仍沿用第一次的岗位和采集时间。

### 13.2 R6：费用未知跨尝试保留

根因：重新排队时把 `open_calls` 清零、`cost` 置为 none，历史上没结清的调用就此丢失。

修复：把记账分成两层。
- 任务整体：`cost`，以及 usage 中的 `calls`、`open_calls`、`tokens`、`late_calls`，跨尝试保留。只要任何一次尝试里有调用没回报用量，任务 cost 就保持 unknown，直到那次调用的用量（包括迟到的回报）到达。
- 当前尝试：usage 中的 `attempt_calls`，重新排队时归零，只决定本次预留的额度能否退回。本次尝试没成功、也没发起过模型调用时就退回本次额度，不受前一次尝试费用未知的影响。
- 迟到的回报：计入总量并结清它自己那一次调用，不改当前尝试的 `attempt_calls`。

测试：
- Codex 本轮新增的回归通过：两次尝试后 cost 仍为 unknown，额度共 4 单位。
- 新增 store 测试：第一次尝试丢失回报；第二次在调用前失败，退回本次 2 单位，任务仍 unknown；第三次调用成功，任务仍 unknown，usage 记两次调用、一次未结清，tokens 只含已回报的部分。
- 新增 runner 测试：调用中途进程被杀，重试成功后任务 cost 仍为 unknown。
- 调整：我上一轮的“迟到回报”测试原先断言重新排队后 cost=none，这正是本轮指出的错误语义，现在改为 unknown，迟到回报到达后变为 known；“重试在调用前失败则退回本次额度”的断言保留。两处用量结构断言加上了 `attempt_calls`。

### 15.1 修复

- **独立的请求记录**：新增 `request_keys(user_id, operation, request_key, input_sha256, created_at)` 表，主键为“用户 + 操作 + 请求键”，记录这个键第一次被接受时所请求的真实输入（规范 JSON 的 SHA-256）。

  - 排了新任务；
  - 要求已经找到，直接返回岗位；
  - 加入同一岗位正在进行的任务；
  - 岗位已保存，但暂时不能排队。

- **同类路由一并修复**：

- **保留不变的行为**：
  - 相同正文换新键，仍然复用已有的岗位和工作。
  - 同一个键重发相同输入，仍然得到原岗位和首次采集时间。
