### C. 取消重试后，实际执行占位丢失

复现：用事件门控让第一个 handler 保持运行 → 取消任务 → 同一请求标识重试 → 旧 handler 仍运行时再次派发 → 释放旧 handler，继续阻塞新 handler。

观察：同用户两个 handler 同时运行；旧 handler 退出后 `runner.idle() == True`，重试任务在数据库中仍为 `running`。

入口：`task_runner.py::TaskRunner._dispatch/_run/idle`；`tenant_store.py::claim_tasks/cancel_task/submit_task`。

实施方向：每次实际执行用 `(task_id, execution_token)` 区分，并记录用户和资源类型。取消使旧 token 失效，但底层调用未退出前仍占实际槽位。派发时同时考虑数据库运行状态与进程中尚未结束的执行。仅改字典键不足以保障同一用户串行。

验收：
- 旧 handler 实际退出前，同用户重试或其他重任务不得开始；其他用户仍可使用空闲槽位。
- 旧执行退出只能释放自己的占位；任何 handler 仍在运行时 `idle()` 不得错误返回真。
- 总并发、PDF 槽位、单用户串行、超时后的占位回收、取消后迟到结果拒绝都保持正确。
- 本次未观察到旧结果覆盖新结果或额度绕过，不将这些未经证实的后果写为根因。
