# Public HTTPS address, one owner

This deployment keeps the single-user database and encrypted data volume from
[the AWS deployment](aws-deployment.md). It adds a CloudFront HTTPS address with a private
VPC connection to EC2. All pages, APIs, previews and downloads require the owner login.
There is no signup, multi-user isolation or public demo. `/healthz` returns only health status.
The original localhost mode remains optional. The first owner workspace was deployed on
2026-09-30 UTC. HTTPS authentication, CSRF protection, synthetic PDF rendering and backup
restoration passed. The owner supplied the DeepSeek secret and a bounded live API call passed;
the remaining operational drills are recorded separately.
See the [acceptance record](aws-acceptance.md).

## Deploy

1. Deploy `deploy/aws/workbench.yaml` following the existing guide, install a tested release
   containing `public_access.py`, and verify its local health check. Never upload `.local`,
   CVs or credentials into the image or repository.
2. Read the EC2 instance's private DNS name and security group and its instance-profile role
   from the base stack. Query the region's managed prefix list named
   `com.amazonaws.global.cloudfront.origin-facing`.
3. Create and review a CloudFormation change set from `deploy/aws/public.yaml`, supplying
   `HostId`, `HostPrivateDns`, `HostSecurityGroupId`, `HostRoleName` and
   `CloudFrontPrefixListId`. It creates a CloudFront VPC origin and distribution, a generated
   owner login secret, permission for this host to read only that secret, and port 8765 ingress
   restricted to CloudFront's origin-facing network. It does not open SSH or a database port.
   Execute the reviewed change set. AWS creates its CloudFront VPC-origin service-linked role.
4. Through SSM run the installed release's
   `/opt/workbench/current/deploy/aws/host/enable-public.sh ORIGIN_PRIVATE_DNS LOGIN_SECRET_ARN`
   using the public stack outputs. It fetches and validates the secret, enables the public
   listener and requires a local unauthenticated request to return 401. A failed activation
   stops the service. CloudFront cannot access private content before this step: the original
   host check rejects its origin hostname.
5. Open the `PublicUrl` output. Retrieve the `OwnerLogin` secret yourself in AWS Secrets
   Manager. The username is `feiran`; the password is generated by AWS. Enter it into the
   browser's login prompt over HTTPS. Never paste it into a GitHub issue or release output.

CloudFront uses managed **CachingDisabled** and **AllViewerExceptHostHeader** policies:
Authorization and CSRF headers reach the app, the origin Host is explicit, and private
responses are not cached. The application still requires its per-start CSRF token after login.
The owner secret is fetched into a protected file under `/run` at service startup. To rotate
it, update the secret in AWS and restart `workbench.service`; existing credentials then fail.
Basic authentication uses the browser's login prompt; closing the private browser session
clears its cached login. A dedicated account portal or MFA is not implemented.

## Acceptance before real data

- HTTPS `/`, `/api/facts`, a preview and a download return 401 without login, even if a CSRF
  token is supplied. Wrong credentials also fail; HTTP is rejected.
- Authenticated `/` works; API requests still require the page token. Chinese and English CV
  uploads and edits work. Synthetic CVs export through the real Chromium renderer.
- Requests to the EC2 public IP from the internet cannot reach 8765. S3 backups remain private.
- Restart the service, verify synthetic saved data survives, then create and restore a backup.
- Check CloudWatch and public GitHub logs contain no passwords, API keys, tokens or CV content.

Only after these checks should the owner upload personal data into the authenticated workspace.
New job data is imported through the app and stays on the data volume. New features are released
as tested container images through the existing manual GitHub workflow; code releases do not
replace the data directory. Each new deployment requires its own DeepSeek secret. The first
owner deployment has connected it and passed a one-request synthetic connectivity check.

## Cost and removal

This adds CloudFront traffic/request charges and one Secrets Manager secret to the existing
EC2, disk, IPv4, backup and monitoring costs. It does not add a load balancer or NAT gateway.
Free credits and budgets do not guarantee zero charges. The existing budget only sends alerts.
Delete the public stack to remove its public entry point; the login secret is retained.
Keep the base stack while the data is needed. Do not delete the encrypted data volume or backups.

AWS references: [VPC origins](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-vpc-origins.html),
[managed origin policies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/using-managed-origin-request-policies.html),
[managed cache policies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/using-managed-cache-policies.html).

## Connect or rotate DeepSeek

Store the raw API key as a plaintext Secrets Manager value, never a JSON wrapper or a repository
file. Set the base stack's `DeepSeekSecretArn` to that secret's ARN and review the change set.
For an already-running host, also update only `DEEPSEEK_SECRET_ARN` in its protected
`/etc/workbench/env`, retaining the owner-login settings, then restart `workbench.service`.
Changing EC2 user data alone does not rerun the initial bootstrap on an existing Linux host.
The service fetches the key into its protected memory-backed file on startup. Later rotations
of the same secret only need a service restart. Verify health, the owner gate and a bounded
synthetic API call; never print the key.
